1 The big picture

When a B2B deal comes in, Savex receives a small bundle of documents – the OEM approval or quote, the partner’s purchase order, the end customer’s purchase order and a credit approval. Someone has to read all of them, make sure they agree with each other, get sign-off for anything odd, and then key the order into the ERP (IFS). This system does that work.

Before

  • Read PDFs and e-mails by eye
  • Cross-check 15–20 business rules by hand
  • Build the Excel loading sheet manually
  • Create part masters and the PO in IFS by hand
  • Easy to miss an expired deal or a duplicate order

After

  • Upload once – the system reads and sorts the files
  • Every rule is checked the same way, every time
  • Excel loading format and PDF report are generated
  • Approvers decide from an e-mail; the ERP load is automatic
  • Hard stops for expired deals, untrusted quotes and duplicates

The journey in six steps

  1. 📤
    UploadCreate a transaction and add the order documents
  2. 🔎
    ReadOCR + AI pull out names, dates, parts, quantities, prices
  3. ✅
    CheckRules compare the documents with each other
  4. 🖊️
    ApproveAnything unusual goes to the right people
  5. 🏭
    LoadA bridge creates the purchase order in IFS
  6. 📬
    NotifyOwner gets e-mails, PO PDF, Excel and J Number
One rule of thumb that runs through the whole system AI is used only to read documents. It never decides whether an order is acceptable – that is always done by fixed, repeatable business rules and by people.

2 Who uses it

Sales Team (role “sales”)Creates transactions, uploads documents, fills the loading inputs, runs validation, fixes and re-uploads, downloads the Excel and PDF. Sees their own transactions.
Support Team (role “support”)Can see every transaction and download the PDF. When mapped as a Level 1 / Level 2 approver for a product line, approves exceptions (warnings and errors).
Business Team / Product ManagerCan see everything, download formats and read the audit trail. Product Managers (approver level 3) decide value and margin escalations straight from an e-mail link – no login needed.
AdministratorEverything above, plus: users, roles, product lines, approver mapping, audit trail, repair tools (re-read a document, fix a line description) and the IFS queue controls.
Ops AdminCreates and manages users only.
IFS Bridge (a system account)A background worker inside the Savex network. It collects approved orders, creates them in IFS and reports back. It is not a person.

A person can hold several roles at once; they get the combined permissions. A user can also be limited to certain product lines (empty = all).

6 The checks, in plain words

Results use five labels: PASS all good · WARNING a person should look · ERROR something is wrong · INFORMATION good to know · NOT APPLICABLE does not concern this order. Limits (quantity tolerance 0.5, price tolerance 1.0, 60-day delivery window) sit in config/validation_config.json.

11.2 What happens inside one validation run

  1. Read what is missing – any file not yet processed goes through OCR → classify → AI extraction. Results are stored per document so they are reused.
  2. Merge – documents of one category are combined; Fortinet FTQ and BDR documents feed the same slots as OEM Approval and IC Approval.
  3. Normalize – one internal order model keyed by part number / config ID; OCR repairs and fuzzy matching.
  4. Reconcile – line totals recomputed; ordering branch derived.
  5. Enrich – house-style descriptions; user-entered fields are carried over; Fortinet billing plan and Singapore rules applied; Savex’s own tax number is never stored as a party’s.
  6. Validate – HPI / HPE engine or Fortinet engine, then the duplicate-order check; a rule that crashes counts as a failure, never a crash.
  7. Save and route – results replace the previous run; status set; gates and approvals applied; owner notified.

11.3 Status tracks

An order carries four independent status tracks:

Transaction status DRAFT→PROCESSING→VALIDATION_IN_PROGRESS→ DOCUMENTS_INCOMPLETEVALIDATION_WARNINGVALIDATION_ERRORREADY_FOR_DOWNLOAD→COMPLETED
Business Team (PM) (blank)→PENDING→APPROVEDREJECTED
Support approval NOT_REQUIREDPENDING_L1→PENDING_L2→APPROVEDREJECTED
IFS loading (blank)→QUEUED→IN_PROGRESS→DONEFAILED

A document has its own states: Pending → Uploaded → Classified → Processed → Validated (or Error / Deleted). A transaction left half-way by a server restart is re-evaluated from its saved results at start-up so it never shows a spinner forever.

11.6 Security, reliability and quality requirements

AreaRequirement as built
AccessEvery API call needs a valid session or Entra token except sign-in and password reset. Permissions are checked on each action. Approval and reset links use random 32-byte tokens that are single-use.
Transport & headersHTTPS in production (strict-transport-security on). Headers: no content sniffing, no framing, no referrer. Cross-origin access is open only outside production.
SecretsNo keys or passwords in source. Values come from the environment, Key Vault references or an encrypted credential store.
Safe errorsUsers see a generic message on unexpected failures; the detail is only written to the log. Document contents are not logged.
ResponsivenessUploads return immediately; OCR / AI and validation run in the background and the page polls for the result.
ResilienceStuck jobs are recovered at start-up · e-mail and in-app alerts are best-effort · bridge steps are idempotent and orphaned “in progress” items are reclaimed at bridge start · re-reads never erase good data.
TraceabilityAudit log for every significant action; validation results are stored per run.
Data retentionUploaded documents and PO PDFs are kept until a user deletes them (optional time-based purge). Transactions, results and audit are never purged by clean-up.
Time zoneTransaction numbers and “today” checks follow India time.
MaintainabilityOne module per concern, replaceable behind a small interface; business rules and master data live in JSON where possible.
TestingAutomated tests cover validation rules, Fortinet rules and lines, approvals, deal-date gate, billing flow, bridge rules, Excel output, vendor e-mail, passwords and more. The release script refuses to deploy if they fail.

11.8 The IFS bridge in more detail

  • Runs inside the Savex network as a Python worker; settings are B2B_CLOUD_URL (default http://127.0.0.1:8000), B2B_BRIDGE_EMAIL and B2B_BRIDGE_PASSWORD. Options --dry-run and --once are available.
  • Environment lock: its Oracle connection is pinned to the SVXREP test replica (SNS01 orders use the SGPREP replica). It refuses to start if the connection resolves to SVXLIVE, and the app rejects results from any other environment.
  • Fortinet purchase orders are split into hardware and software, with their own address, delivery-terms, ship-via and Location-Group profiles, and the numbered PO header notes written to the PO. Coterm / renewal parts get the required commodity groups and tax code.
  • After creating a PO it checks its own work (PO lines vs loading rows), renders the PO PDF, and reports DONE or FAILED with the full step log.
  • It also refreshes J Numbers from IFS and re-aligns part descriptions between the app and IFS in small, budgeted batches.

13 Open points

These are observations from the current files, not requirements. They are listed so that the documents and the system say the same thing.

#ObservationSuggestion
1Hosting story differs between documents. deploy.ps1 and the documentation portal deploy to Azure App Service, while the README and .env.example describe a local / on-premises setup (SQLite or on-prem Postgres, local storage). docs/ARCHITECTURE.md still lists PostgreSQL Flexible Server and Blob storage.Confirm what production actually uses and align the README, ARCHITECTURE and DEPLOYMENT guides.
2Retention. Some older text says source documents are deleted after 2 days. The code default keeps them indefinitely (SOURCE_DOC_RETENTION_HOURS=0).Update the older wording; set a value only if the business wants a purge.
3Rule counts. The older portal says 19 rules; the HPI engine has 20 (plus the duplicate check). A Fortinet code comment still says “11 rules”; the rule list has 14.Refresh the portal and the comment.
4Manual “confirm document type” endpoint is not reachable. confirm_classification in app/api/routes_transactions.py has no route decorator, so a low-confidence document cannot be confirmed through the API.Add the route decorator (and a test), or remove the function if the upload slot always sets the type.
5Defaults to change before real use. The default password for new users and the session-signing secret have development values. In local sign-in mode, an X-User-Email header is accepted for testing.Use Entra mode or a strong secret in production, and make sure the header shortcut is not reachable.
6Unused approver block. validation_config.json contains an “approvers” section with placeholder addresses that no code reads; approvers actually come from Admin → Approver mapping.Remove it to avoid confusion.

Glossary

B2B
Business-to-business order placed through a partner (reseller).
OEM / OPG
The manufacturer’s approval for a special-price deal – HP calls it the Order Processing Guideline.
EOP
The deal / quote reference on the HP approval, used as the order’s reference number.
FTQ
Fortinet Quote – Fortinet’s approved quote, the base document for Fortinet orders.
Partner PO (PPO)
The purchase order the reseller sends to Savex.
End Customer PO
The purchase order the final customer gave the reseller.
BDR / IC Approval
Internal credit approval for the partner and order value.
License Sheet
Fortinet spreadsheet listing licences, customer and website details.
Loading Format
The business’s order-loading e-mail / sheet; also the name of the Excel the system generates.
Loading Location Site
The 5-character site code where the order is loaded in IFS (e.g. MUVPU, CHG04).
BT (Branch Transfer)
Billing route where goods are loaded at one site and transferred to another before billing the customer.
IFS
The ERP where part masters and purchase orders are created. SVXREP / SGPREP are test replicas.
J Number
A reference IFS assigns to the PO line after creation; the owner is e-mailed when it appears.
RDD
Requested Delivery Date.
RNW / Coterm
Fortinet renewal and co-terminous licence lines (named with a -RNW or COTERM prefix/suffix).
OCR
Turning a scanned page or PDF into readable text and tables.
RBAC
Role-based access control – what each person is allowed to do.
Bridge
The on-premises worker that carries approved orders into IFS and brings the result back.
